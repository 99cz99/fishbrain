# 记忆系统及联动全面审查

日期：2026-10-29。对象：当前工作区 Fishbrain 记忆 v2 及人格成长更新后的代码，包含已有未提交修改。

## 结论与范围

主干已经接通，但不能判定优先级、语义与模块联动均正确。本次发现 12 项问题，其中 5 项 P1、7 项 P2。P1 表示应优先修复的明确功能缺陷或信任边界问题，不表示都已造成线上事故。

检查覆盖 memory、memory_system、personality、autonomy、life、QQ 消息与发送路径、审批执行、小黑盒适配器、HTTP 管理接口、Flutter 记忆与设置界面、安装资源、迁移与测试。参考当前 CLAUDE.md、记忆文档、人格更新记录及其指定设计文档。

本次只新增报告，没有修改业务代码、真实数据库或配置；没有连接手机、重启、部署、发送外部消息或调用真实模型。下文“复现”均为临时内存库、模拟模型或独立加载本地安装资源，不能替代手机现场及真实模型验证。

## 发现（按修复优先级）

### 1. P1：安装资源与主源码不同，配置城市后生命状态读取直接报错

位置：`fish/memory.py:399`、`app/assets/fish/weather.py`、`app/assets/fish/life.py`、`app/lib/pages/wizard.dart:200`。

全量比较 fish/*.py 与安装资源，发现 life.py、weather.py 不一致。安装资源中的 weather.py 没有 get_weather_mood，而同步过的 memory.py 在 city 非空时直接调用它。

复现：新进程仅从 app/assets/fish 导入 Store，设置 city='audit-city'，调用 get_life_state，抛出 `AttributeError: module 'weather' has no attribute 'get_weather_mood'`，不需要访问天气服务。

安装资源中的 life.py 还缺少四维情绪更新、记忆情感传染及对应提示内容。由部署向导写入的运行时因此不能等同于 fish/ 主源码。已有副本一致性测试仅比较六个模块，没有覆盖这两个文件。

建议：统一资源生成入口，对全部运行模块做清单、接口与内容一致性检查，并对资源目录独立执行最小启动与状态读取测试。当前手机是否使用这些旧副本，本次未核实。

### 2. P1：外部记忆正文直接进入 system，数据与行为规则没有可靠分界

位置：`fish/qq_bot.py:1250–1286`、`fish/memory.py:163`。

retrieve 会返回原始 episode；format_memory_line 原样输出正文，随后拼入与人设相同的 system 消息。“背景资料，不是新指令”只出现在工作摘要标题，长期记忆没有统一的数据封装和优先级约束。对话原文中的换行、伪造规则标题、指令性文字都会被带进 system。

这确认了外部正文进入高信任消息的路径；没有进行真实模型攻击测试，不能声称已成功操控模型。

建议：system 仅放固定规则与可信设定；召回以结构化、明确标记的不可信资料提供，统一规定其中指令不得执行。所有聊天、反思、成长及行动入口使用同一封装与规则。分离角色本身也不能完全消除提示词注入，需要回归样例验证。

### 3. P1：替换事实未使旧原话退出“当前知识”，新旧偏好同时召回

位置：`fish/memory_system.py:130–158、231–241`、`fish/memory.py:163`。

replaces 将旧 fact 及其下游置为 superseded，但旧 fact 的来源 episode 仍为 active。retrieve 对所有 active 类型统一打分，旧原话仍能成为高相关结果；普通记忆行又没有日期、来源 ID 或历史标记。

复现：“我喜欢咖啡”提炼成事实后，再用“我现在不喜欢咖啡”替换。召回仍同时得到旧 episode、新 fact、新 episode。旧话相关性更高时甚至排在新事实之前。

建议：保留历史证据，但区分“历史曾说过”与“目前有效”；当前事实查询优先有效版本，历史事件附时间和已被纠正标记。不要为了消除冲突直接删除历史来源，人物成长仍需要它们。

### 4. P1：先截断混合记录、后筛类型，使事实更新和反思在正常聊天量下失效

位置：`fish/autonomy.py:290–291、469–498`。

提炼器先取同人物同范围最近 50 条任意记忆，再筛 fact/intention。50 条原始闲聊即可把更早的事实、待办全部挤出输入，模型无法用 replaces 更新、完成或取消它看不到的旧记录。

反思先取全库最近 300 条，再筛 fact/experience；原始事件同样能挤掉全部合格依据。即使没有对任何证据调用模型，也会扣掉本轮全部积分、写入最近反思时间。

复现一：一条旧事实后插入 50 条同人物 episode，捕获提炼提示词，已有事实和事项为 []。

复现二：三条自身经历后插入 300 条 episode，反思积分设为 30，执行后模型调用为 0，积分却归零。

建议：在 SQL 中先按类型和资格筛选，再分页/限量；按人物与范围公平调度。仅在实际检查合格证据后消费对应积分，保留没有处理的证据与积分。

### 5. P1：缺少“敏感信息不主动记住”的提炼约束和写入兜底

位置：`fish/autonomy.py:294–312`、`fish/memory_system.py:179–240`。

权威设计明确要求密码、身份证等敏感信息不主动记。当前提炼提示词未包含这一要求，数据库候选校验也不检查这类内容。人格公开审查中的“密码”等过滤只适用于人格条目，不能保护普通事实。

复现：将完全虚构的 `test password = DEMO_ONLY_ABC` 作为事件与候选事实提交，事实被成功持久化。未读取或使用真实凭据。

建议：明确原始短期消息、原始事件与主动长期提炼的不同保留政策；至少在提炼和事实写入两层阻止秘密凭据长期化，增加脱敏与真实误判样例。范围保密不能替代“不主动存储”的要求。

### 6. P2：待处理事件调度从最新 100 条中选“最旧”，真正旧积压可能长期饥饿

位置：`fish/memory_system.py:45–48、170–177`、`fish/autonomy.py:64–70`。

_rows 默认 id DESC，pending_episode_batch 先取最新 100 条，再在其中选最旧人物组，最多处理 10 条，每轮后睡 30 秒。早于这个窗口的事件没有调度优先权。单轮理论上限为 20 条/分钟，实际还要加模型耗时；持续流量足够大时旧事件会一直排不上。

复现：先插入人物 A 的事件 #1，再插入人物 B 的 100 条事件，均满足等待时间；首批选择 #2–#11，没有选择真正最早的 #1。

建议：按最早未处理事件定位组，再读取该组批次；增加积压数、最老等待时间、失败重试次数和公平性指标。批处理失败使用退避，避免单组错误反复消耗额度。

### 7. P2：后台处理稍晚于约定时间，会把明确到期时间永久清成 0

位置：`fish/memory_system.py:220–230、275–284`。

写入只接受 now < due_at < now+366天，否则 due_at=0；但跟进查询本来支持过去 7 天内的到期事项。两处时间规则互相矛盾。30 秒等待、模型耗时或服务重启都可能让真实约定在处理时已经过期。

复现：为 120 秒前的事件提炼一个 60 秒前到期的明确约定，落库 due_at=0，后续永远不会成为到期事项。

建议：区分“未知日期”和“已明确但已到期”；允许合理回溯窗口的时间落库，由调度规则决定是否跟进。同时区分事件真实时间、接收时间和处理时间；QQ 当前写入没有使用平台事件 time，重放时会偏移时间理解。

### 8. P2：聊天与主动行动使用不同人格、记忆上下文，第二阶段行动丢失起因

位置：`fish/qq_bot.py:81–108`、`fish/life.py:164–179、189–238`。

聊天注入 persona 与 self_profile；心跳、行动仅注入 self_profile，没有注入用户底层 persona。行动阶段只收到 drive、画像和到期事项，没有携带第一阶段看到的相关记忆及选择该 drive 的起因。

复现：设置独有 persona 标记，生成 _action_prompt，标记不存在。心跳能看到 private 范围的普通事实，但行动提示没有把相关背景受控地传下去。

后果是自动画像尚为空时，主动行为几乎只有通用性格；第一阶段“想起某件事”也不能保证第二阶段知道具体是什么。内部全范围读取不直接等于外泄，但输出到主人或公开平台前缺少统一的目标范围裁剪步骤。

建议：共享人格渲染器，并为一次行动携带结构化起因、必要证据和目标可见范围。内部可见与对外可说分开校验；不能简单把所有私人记忆加入公开发帖上下文。

### 9. P2：手动移除自动特质只影响当前行，后续可用相同证据重新生成

位置：`fish/personality.py:34–43、80–122`、`fish/autonomy.py:412–447`。

编辑器移除自动条目后，将旧行设为 manual_removed；生成与写入只检查当前 active 特质，没有读取用户移除记录。模型看不到“这条特质曾被用户否决”，写入也不阻止复活。

复现：生成“坦率表达判断”，编辑器改成手动“温和表达分歧”，再次提交旧特质候选后返回新增 1，最终两条同时存在。

建议：保留用户否决/覆盖记录并纳入生成和存储校验；为人工画像与自动画像定义冲突优先级。是否允许将来在新证据下重新提议，应与自动直接恢复区分。

### 10. P2：稳定身份只存在数据库中，喂给模型时又退化为昵称

位置：`fish/memory.py:163–170`、`fish/qq_bot.py:1250–1266`、`fish/memory_system.py:263–273`。

普通召回仅输出 kind、subject、content，不输出 entity_id、scope、时间或依据。owner 全渠道和群聊都可能同时召回多个同名人物的事实，模型无法仅凭昵称判断分别属于谁。自身 experience 还可能在正文中包含“对方原话”，当前渲染不足以明确事件参与者。

复现：两个不同 qq ID、不同私聊范围、相同昵称与事实，在 owner 召回后渲染成完全一样的两行。

建议：使用稳定的对话内人物代号，保留来源范围、时间及认识类型；与当前说话人明确关联。无需向公开回复暴露真实账号，模型内部身份区分与对外显示应分离。

### 11. P2：发布、评论等实际结果没有进入统一自身经历链路

位置：`fish/server.py:216–259`、`fish/heybox.py:286、313`、`fish/autonomy.py:189–204、238–268`。

QQ 正常回复和主动文字发送已有 record_self_experience；审批通过后的空间发布、小黑盒发帖/评论及大部分平台动作，仅执行或写诊断日志，没有把最终成功、失败、未确认结果记录为有来源的自身经历。

这使“统一智能体记忆”目前主要覆盖 QQ 文字交流，人格成长无法稳定吸收它在其他平台实际做过的选择。诊断日志也不应反过来当事实补洞。

建议：在动作实际完成端统一产生结果事件，区分请求、审批、执行与平台确认；敏感内容继承范围。不要把“线程已启动/审批已同意”记为发布成功。

### 12. P2：自身经历没有活跃数量管理，召回对所有活跃记忆全量扫描

位置：`fish/personality.py:45–62`、`fish/memory_system.py:102–117、130–155`。

_prune 管理已处理 episode 及 fact/user/person/belief，不管理 experience；record_self_experience 本身也不触发归档。retrieve 默认 candidate_limit=None，对全部可见 active 记录做字符相关性排序，并占用共享 Store 锁。

长期聊天越多，活跃自身经历越多。每条经历又复制原话与回复，增加磁盘和扫描开销。当前没有测量真实手机性能，不能给出具体卡顿阈值，但增长路径和扫描复杂度已由代码确认。

建议：自身经历分层归档，历史证据继续保留并可追溯；检索用 SQLite FTS 等候选召回后重排，避免简单“只留最新 N 条”造成长期知识再次不可达。用真实规模数据测量查询耗时、锁等待、数据库体积。

## 优先级与语义的统一规则建议

不宜只把所有数据排成一个 importance 分数。至少分三个轴：

1. **行为权限**：程序硬约束、当前明确的用户控制优先；外部消息和记忆正文始终是证据，不能通过提炼升级为系统指令。
2. **自身人格**：用户底层 persona 与明确人工覆盖优先于自动特质；短时心情影响表达，不自动改写长期人格。人格互相矛盾时应形成待审冲突，不同时无说明注入。
3. **世界知识**：同人物、同事实槽位中，有效纠正与新版本优先；历史事件保留时间限定；belief 始终标为暂定；未知不能用高 importance 补成事实。当前用户新陈述仍需经过身份、事实与时间判断，不应无条件覆盖所有旧知识。

evolve 当前允许自动修改 midnight_ok、approve_money、approve_publish 等用户可编辑开关。这与设计中的软设定自治有关，不能仅凭本次审查断言违反产品意图；但人工明确限制与自动进化之间没有“用户锁定”的优先级。内存库模拟已确认 midnight_ok=false 可被 evolve 输出改成 true。建议区分可自主偏好和用户锁定控制，审批是否必须执行仍以执行端硬约束为准。

字符相关性阈值 0.08、importance、新近性和人物加分是启发式召回，不具备同义、否定、时间推理能力。尤其需要“以前喜欢/现在不喜欢”“我/他/引用别人”“昨天说明天”“同名不同人”“这周已结束”的真实样例集。可以先增加 FTS、时间字段和版本关系，再比较向量检索是否确有收益，不必先引入大型基础设施。

人格成长还有反馈回路风险：它按当前画像生成回复，再把这些回复作为自身行为依据提炼画像。当前“独立根事件”主要保证来源不重复，不保证模型输出在统计上独立，也不保证体现自主选择。建议区分请求驱动、复述、工具结果、实际选择及外部反馈，衡量跨时间稳定性，避免把重复台词当成长。

## 已正确接通的部分

- 事件先落库、提炼后台进行，普通回复不等待提炼完成。
- 稳定人物 ID、同人物/同范围来源验证，以及主人在群里仍按本群召回，已有代码和回归支持。
- 原始证据与 fact/belief 分离；替换、删除、重放墓碑及生成期间删除的基本约束已实现。
- 私有经历不会直接作为公开人格注入；人格候选有独立审查、根事件数约束和写入前再验证。自由文本隐私质量仍依赖模型。
- 关联删除可撤销支持不足的自动画像，正常归档可保留人格历史依据；无关纠正不再全量清空画像。
- 画像保存有版本冲突保护；App 会读取最新画像并轮询成长状态。
- 带 intention_id 的跟进有原子领取、近期互动抑制及未确认不自动重发保护。自由生成的无 ID 主动聊天不受同等约束，这一点文档已有说明。
- HTTP 记忆与设置端点有认证；App 展示来源、范围、历史状态，提供分页、纠正、删除和待办完成/取消。

今天早先“画像只读取 global/self belief”“无关删除清空画像”“自身经历不增加积分”“编辑器没有版本保护”等问题，在当前代码中已经修复，本报告没有把旧报告的结论当成新缺陷重复计算。

## 验证结果与修复顺序

- `python -m unittest discover -s fish/tests -v`：85 项通过。
- `flutter analyze --no-pub`：无问题。
- `flutter test --no-pub`：12 项通过。
- 额外内存库复现：新旧事实同时召回、已有事实窗口遮挡、反思空跑扣积分、积压队列顺序、到期时间归零、人工移除特质复活、身份渲染丢失、软设定覆盖和模拟秘密凭据入库。
- 独立资源运行时复现：配置城市后读取生命状态抛出 AttributeError。
- 全量资源比较：life.py、weather.py 不同，其余当前 fish/*.py 存在对应资源且字节一致。

建议修复顺序：先修安装资源与运行时接口；再修检索版本与信任边界、先筛选后限量及敏感信息策略；随后修待办时间、积压调度和人工优先级；最后补统一行动上下文、跨平台结果事件、归档检索及真实语义评测。

这些测试验证程序行为，不能证明模型对私人信息、日期、否定和人格的判断正确。下一轮应把本报告的最小复现转成针对实际缺陷的回归，再用匿名样例评估语义质量。
