## 结论与此前判断的更正

1. WebUI 快捷登录与 `-q` 冷启动登录最终使用同一个 NTQQ 原生登录能力。WebUI 是现有进程的控制入口，不是另一个 QQ 凭据仓库。
2. WebUI 控制凭证失效、QQ 登录进行中、OneBot 未连接、QQ 原生凭据不可用是不同故障，当前鱼脑会把多个故障汇入“重启再快登”，能够破坏本来可恢复的会话。
3. **撤回“Login 目录内的 0 字节文件就是未落盘 keystore，因此必须 chroot”的根因断言。**目前只证实两个文件为空，未证明其文件角色、真正票据存储位置或失败的原生写入调用。它们可能是占位/锁/辅助文件，也可能与登录持久化有关，均需进一步取证。不能把候选解释写成事实。
4. 已找到并用隔离复现证实控制代码缺陷，优先修复这些缺陷，再用受控实验判断持久化根因。没有证据支持现在就重做容器、伪造设备 JSON、重置设备标识或给空文件随意填内容。

## 一、把几类“凭据”和选择项分开

| 项目 | 用途 | 能否直接证明 QQ 可免扫码 |
|---|---|---|
| 鱼脑 `.api-token` | 授权 App 操作鱼脑 API | 不能 |
| NapCat WebUI token → 哈希 → Credential | 授权鱼脑操作 NapCat 控制接口 | 不能，它不替代 QQ 登录票据 |
| `qq_quick_login_uin`、`-q`、WebUI `autoLoginAccount` | 指定要尝试登录的账号 | 不能，它们是账号选择项 |
| 原生登录列表及 `isQuickLogin` | QQ 原生服务当前报告的候选账号 | 是能力线索，仍需看原生调用结果；当前进程列表不等于冷启动后的列表 |
| QQ 原生票据、设备绑定及相关存储 | 支持 QQ 服务重新认证 | 实际位置、有效性和跨重启行为需要核实 |

OneBot 8081 则是登录后供鱼脑使用的业务连接。QQ 已登录而 OneBot 未连接时，应先修复适配器/传输配置，不能直接重做账号登录。

## 二、实际调用链

### A. 已有进程中的 WebUI 快捷登录

```text
App 登录页“快速登录”
  → POST 鱼脑 /qq/quick_login
  → 检查 QQ 进程、WebUI CheckLoginStatus
  → 读取 WebUI token，计算登录哈希，换取控制 Credential
  → GetQuickLoginList，选择目标账号
  → SetQuickLogin
  → NapCat 登录回调
  → NTQQ 原生 quickLoginWithUin
  → 原生结果 / 登录回调 / 初始化完成
  → OneBot 连接，鱼脑确认账号可用
```

设备 bundle 关键位置：`41662–41678`（列表与回调转发）、`49821–49842`（控制路由）、`83078–83093`（原生登录调用）。WebUI 请求不负责生成、导出或另存一套 QQ 票据。其成功响应也不应代替后续 `ready` 和传输状态确认。

`SetQuickLoginQQ` 是另一个接口，只更新 WebUI 的自动登录账号设置；它和立即发起登录的 `SetQuickLogin` 不可混用。`GetQuickLoginList` 也不是凭据下载接口。

### B. 跨完整进程重启的免扫码登录

```text
启动 proot 容器内的 QQ/NapCat，并传 -q 目标账号
  → 解析 QQ 数据目录与 global 目录
  → 初始化原生登录服务及其 commonPath、版本、主机参数
  → 原生 getLoginList 加载历史记录
  → 确认目标账号在记录中，调用同一个原生快捷登录能力
  → 原生模块使用能读取的票据及设备身份进行认证
  → 接受登录后初始化核心，最后建立 OneBot
```

设备 bundle `82952–83000` 推导路径及初始化登录服务，`83218–83252` 处理命令行账号及列表，`83347–83356` 加载启动时的历史列表。冷启动能否成功，关键在“新进程实际加载了什么、原生调用返回什么”，不在 WebUI 有无保存控制 Credential。

原生路径由 `getNTUserDataInfoConfig()` 返回值优先决定，缺失时才回退 HOME 下的 QQ 目录。Linux global 为 `<dataPath>/global`。必须先确认这个实际路径，再分析文件；仅检查一个猜测路径不足以判定未落盘。

### C. 无 -q 时的 WebUI 自动选账号

设备 bundle `70816` 附近按环境账号或 WebUI `autoLoginAccount` 选择账号，再进入相同的原生登录回调。这是另一种启动选择方式，不是新的认证机制。某些包还实现显式配置的密码回退，但它属于另一种登录方式，会遇到验证码、新设备验证等状态，不能当成“凭据持久化已修复”。鱼脑当前未实现这套密码/验证交互，本方案不建议临时把密码塞入配置来掩盖原问题。

本机 WebUI 自动账号当前为空，而鱼脑有保存账号：这是两个独立选择项。配置 WebUI 自动账号可以改变“无 -q 时尝试谁”，不生成原生票据；使用 -q 的鱼脑冷启动也不以该 WebUI 选项为前提。

## 四、修复的状态优先级

不能把下列规则简单写成一个顺序 if 列表。应分三层处理：

1. **用户期望与操作归属**：明确停止、启动、目标账号变化、平台禁用先更新期望状态和操作代次。明确停止撤销旧启动/登录操作；内部为重启执行的 stop 不等于用户要求永久停机。旧任务在每个发送登录请求、写配置、发信号、启动进程的动作前重新验证归属，不能只在写回结果时检查。
2. **推进已有任务**：同一操作管理器处理登录、换码、配置应用、停止和自动恢复。任务进行中仍持续读取状态、处理验证要求与截止时间；不能因“有任务”就跳过这些反馈。明确拒绝/需验证必须及时结束或转入等待人工阶段。
3. **选择新的自动动作**：仅在没有有效在途任务、用户期望允许、证据属于当前进程/账号代次、冷却及熔断预算允许时选择动作。账号已认证而传输不可用时修传输；已接受扫码、初始化和重连时观察；动作结果未知时查询状态；明确可快登时提交一次；真正退出或长期无响应时才进入受控启动/恢复。

操作超时不等于原生请求已经取消。旧请求可能继续执行，应标记结果未知并核对实际状态；不得仅清除 self_healing 就自动发起另一次登录。鱼脑自身重启后，也须把未完成任务与实际 QQ 进程重新核对，不能复用旧任务的成功结论或自动重放动作。

### 方案复核：必须明确的语义与交付门槛

- **优先级调整**：F11 的互斥、取消和代次保护提升为 P1，是修其他生命周期问题的基础。F05 的鉴权缓存修复应与 P1 恢复流程同时交付；F12 的真实备份清单和一致性验证是执行冷启动实验的前置门槛，不能留到实验之后。
- **四种结果分开**：鱼脑返回排队成功，只表示接受了控制任务；WebUI SetQuickLogin 的成功是该包等待原生调用后报告成功，不能将它降格为仅 HTTP 已提交；native 成功后还可能初始化；核心 ready 和 OneBot 可用须分别观察。
- **账号与传输分开验收**：原生认证成功且当前账号核心 ready，即可判断本次免扫码认证成功；OneBot 断开不能把它改判为认证失败。App 完整业务恢复还需要当前代次的 OneBot 连接和账号身份匹配。
- **未知必须保留**：现有 `_qq_really_online()` 允许 account_online=None，而接口 online 又聚合 WS 与 self_id。新接口必须明确该兼容布尔值代表什么，新增账号/传输分层状态、证据来源、采样时间和进程代次；不能把 None 直接解释成明确在线或离线。旧 WebUI 状态、二维码或 WS 回报不能覆盖新代次。
- **目标账号与观察账号分开**：`qq_bot._on_meta()` 会把收到的 self_id 写入 qq_quick_login_uin。实施时必须明确该字段是“记住上次账号”还是“用户指定目标”，避免只改控制器却被回报路径覆盖新选择；用户目标变化应使旧登录任务失效。
- **持久化期望与临时状态分开**：应定义明确停止在鱼脑重启后的保持策略；运行中的任务不能靠一个持久化布尔值恢复执行。任务标识需包含服务实例/代次，启动时做实际状态核对。

## 五、真正查清跨重启持久化的方法

### 第一步：不退出当前会话的取证

核对实际 QQ/原生模块/NapCat 版本与包哈希、启动参数、HOME/XDG 配置、原生 dataPath/commonPath。对空文件确认 inode、打开它的进程、fdinfo 与锁记录。当前 Android 权限阻止了这些读取，需要在允许的 Termux 进程上下文或隔离调试环境补证；不能将访问失败等同于不存在。

记录现有 GetQuickLoginListNew 的候选状态和查询结果类型；仅记录账号别名与错误码，不导出票据内容。设备指纹应记录摘要与是否变化，不把 MAC/GUID 等私人标识写入公开报告。

### 第二步：先修控制链路，再做一次完整冷启动对照

先在不扰动会话时确认实际资料范围、备份目标、可读性、容量及恢复方法。在线复制只能视为原始证据副本，不能直接宣称一致性备份。预留用户可能需要再次扫码的窗口；先优雅退出并确认所有相关原生写入进程已经停止，再对真实资料、设备身份和配置做成组快照，核对清单、缺失项与校验值，完成后才启动冷试验。系统保护的身份/密钥若不能随文件复制，须明确备份边界与恢复未验证状态，不能承诺文件复制必然可回滚认证。

保持同一 QQ/NapCat 版本、UID、HOME、dataPath/commonPath、machine-id、设备资料和账号；仅启动一次带 -q 的新进程。通过 PID 与启动时间确认完整旧 QQ/登录服务进程已经退出；仅重启鱼脑或 NapCat worker 不等于验证了完整 QQ 冷启动。

按顺序记录：冷启动历史列表 → 原生快捷登录结果/错误类别 → 当前账号核心 ready → OneBot 连接。分别给出结论：

- **免扫码认证**：新的完整 QQ/登录服务进程无人工扫码、原生结果及当前账号 ready 均确认，才算本次认证测试通过。
- **业务可用**：在认证通过的基础上，当前代次的 OneBot 连接和身份匹配，才算 App/鱼脑完整业务恢复。
- 一次优雅重启通过，不等于已经证明 Termux 被强制回收或手机重启后的恢复也可靠；这些故障模式应分别安排验证并报告范围。

| 对照结果 | 应采取的修复 |
|---|---|
| 新进程使用了不同的资料路径 | 统一启动身份、环境与 commonPath；在备份后处理旧新目录兼容，不能直接混合复制密文 |
| 原生列表有账号、调用成功，只有 WS 离线 | 修 OneBot 配置与传输，不再折腾票据 |
| 原生调用实际完成，但鱼脑先超时并重启 | 修 F03/F04/F09 的任务状态与超时语义 |
| 权限/空间/文件系统写入错误被明确捕获 | 修该具体文件操作及路径，随后让 QQ 原生服务重新生成资料并验证 |
| 原生明确返回票据过期/设备验证/风险要求 | 展示原始类别并进入官方扫码/验证流程；不能用写文件或换 WebUI token 绕过 |
| 只有 proot 环境可稳定复现原生系统调用限制 | 再做匹配版本和资料的环境 A/B 对照，评估受支持 Linux 部署或 chroot；目前没有这样的定案证据 |
| 某个 0 字节文件被证实为锁/占位 | 撤销其“凭据健康指标”，转而监测真正认证资料及原生结果 |

### 第三步：上线验收

先覆盖停止失败禁止启动、启动器误识别、未知请求结果、初始化阶段保护、跨进程 WebUI 缓存失效、空/未知列表和重复点击等回归；再分别验证 WebUI 软恢复与一次完整进程冷恢复。扫描成功不能替代冷恢复测试，控制任务排队成功、原生调用成功、认证 ready 与 OneBot 业务可用必须分别断言。还应覆盖停止抢占旧登录、重复点击、服务中途重启、原生结果迟到、目标账号变更、初始化超时和业务传输单独失败。

## 六、联动更新范围

- 鱼脑：建议抽取 `QQController`/操作管理模块，改生命周期、鉴权缓存、结果类型及状态 API；`server.py` 保留 HTTP 适配。若新增模块，同步所有部署 MODULES 白名单。
- App：`api.dart` 的类型化错误、`login.dart` 和部署页的任务显示、冷/热恢复文案、重复点击保护。不能仅改后端还保留“已发起=成功”的界面。
- OneBot：`qq_bot.py` 的生命周期回报、账号观察及保存目标的路径也须联动；把账号状态和业务传输状态分别展示。配置应用、自动保活和必要重启都接入同一操作管理器，不能只替换手动按钮后端。
- 部署兼容：先准备新旧客户端都可理解的响应与状态字段，确定支持的混合版本组合；配套后端模块整体切换，新增导入不能早于对应模块安装。源文件、App 及状态数据的回退边界要一致，不能只回退一份 server.py。
- 资源与版本：同步全部 `app/assets/fish`、向导清单及部署脚本，更新 App 版本并核对 APK/设备实际版本；避免只安装 APK却没替换 Termux 源码。
- 数据/API：定义兼容的 online 含义，分开 desired_state、账号状态、传输状态及 operation（含任务实例、代次、阶段、错误类别）。新增服务器内部状态须联动 `/settings` 写入保护、验证和 UI 模型，不能让一般设置保存覆盖任务控制信息。可沿用已有设置 JSON，但必须明确默认值及鱼脑重启后的恢复语义；真正的原生资料迁移另行验证。
- 文档与知识：撤回“0 字节必然是票据丢失”“device.json 根因已定位”“chroot 已证实为唯一解”等未经验证的断言；注明 Linux/Windows/macOS 设备接口差异。

以上各节为修复前审查和方案。后续用户已授权执行，已替换手机运行源码、升级 App 并完成一次有备份门禁的 QQ 完整进程冷启动；未使用密码登录或修改设备标识。执行范围和证据见本文开头及 v1.0.46 记录。
