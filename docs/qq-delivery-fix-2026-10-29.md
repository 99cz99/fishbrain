# QQ 分段发送、上下文和图片修复记录

## 实际变化

原问题是第一段已被用户收到，但 NapCat 先返回超时，鱼脑抛异常退出整个发送循环，剩余段落未提交，且整轮助手回复未写入短期上下文。下一轮因此可能重新回答旧问题。

新增 `qq_delivery.py`，把每段的发送计划和状态存入同一个 SQLite 数据库的 `qq_outbox`。发送前写入 sending 与带未确认标记的助手上下文；确认后原位更新为实际内容，避免部分成功整轮丢失。只规划尚未提交的内容不进入聊天历史。日志最多保留约 5000 条已终结发送记录，尚未确认的记录不自动重放。

接收线程继续优先处理 API echo，并把自身消息交给确认处理，不触发聊天回复。发送线程能在等 API 时消费自身回报；账号、目标会话、发送时间、精确内容和唯一候选均需匹配，消息 ID 唯一去重。只对稳定的 text/face/at 段做内容匹配，不猜测图片 URL 与本地图片的对应关系。迟到的成功 API 响应通过原 echo 关联。

手机 NapCat 4.18.41 的调试日志在添加 target_id 之前打印 OB11Message；源码确认网络推送前会用原始 peerUin 补入目标，真机历史原始记录也具备可用的 peerUin。因此私聊匹配使用网络回报 target_id，而不是把 user_id（自身账号）误当成目标。

NapCat 发送 baseTimeout 提高到至少 30 秒，鱼脑 API 等待 45 秒，未知后补等回报最多 30 秒。同一会话新消息可提前结束等待；新消息、记忆版本、人设、平台开关、账号变化和停止信号都会阻止旧尾段继续发送。较旧排队用户消息保留为记忆，但已有更新用户消息时不再单独回复。

进程重启将 sending 转为 unconfirmed、queued 转为 cancelled；不会自动补发。确认晚于整个等待窗口时仍可补记上下文，但已取消的尾段不恢复。忘记或重置会清除发送日志正文和匹配信息，迟到回报不能恢复已删除的上下文。平台明确拒绝与正常取消分开记录。未确认主动消息不再形成“成功发送”的人格成长依据。

## 图片

新增 `qq_media.py`：通过严格校验的 MD5 文件标识，在 QQ 原图目录查找文件并验证实际字节 MD5；支持受限容器缓存路径映射、图片头校验和 20 MiB 上限。URL 失败不会跳过 API 本地文件，API 失败后会再次尝试原图缓存。错误日志不记录完整签名 URL、图片密钥或私有路径。

真机读取 17:35 故障图片成功：1,258,022 字节，JPEG。外部 Rkey 服务的返回格式/TLS 故障未被修改；修复通过已有 QQ 原图缓存绕过本例故障。如果新图片没有本地原图且远程服务仍不可用，仍可能失败，但会有明确的脱敏错误来源。
