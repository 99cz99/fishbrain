# 记忆系统资料核对与方案选择

调研日期：2026-10-31。只查论文、作者仓库、官方文档、模型作者说明；未安装框架、未上传真实聊天做外部测试、未修改手机。本文的兼容性与成本判断属于针对本项目的工程分析，未经 Termux 安装及性能实测。

## 结论

推荐保留手机上的 SQLite 数据与现有平台控制，采用 Hindsight 的多路取证思路、Graphiti 的时态与来源建模、MemGPT/Letta 的少量常驻记忆分工，重构为一个本地 MemoryService。先用统一匿名数据比较其与现有实现，再决定是否把成熟框架作为后端。

如果未来允许增加常开电脑/服务器，优先将 Hindsight 作为外部对照后端。当前不推荐直接把整套记忆基础设施塞进手机，也不推荐为修记忆而替换整个智能体运行时。以上是选型建议，不是已经测出的质量排名。

## 1. 核对到的方案及其实际边界

### Hindsight：最值得借鉴的整体读写分工

论文区分世界事实、智能体经历、综合认识与信念，并提供 retain/recall/reflect 分工。这正对应本次“自己的旧解释混入用户证据”的问题。[作者论文](https://arxiv.org/abs/2512.12818)

官方检索实现采用语义、关键词、关系、时间等通道，先进行排名融合，再重排。排名融合避免直接相加不同检索器不可比的分数；排序本身并不证明内容真实。[检索架构](https://hindsight.vectorize.io/developer/retrieval)

API 可以额外返回原始来源 chunks 和 observation 的贡献事实，也明确标记来源是否因预算被截断。这一点比只交给模型 source_ids 更接近我们需要的来源核对能力。[Recall API](https://hindsight.vectorize.io/developer/api/recall)

安装文档列出 PostgreSQL 及向量扩展，也有 pg0 嵌入式 PostgreSQL；支持矩阵包含 Linux ARM64，但未列 Android Termux。不能把“嵌入式”理解成没有数据库依赖，也不能据 Linux ARM64 推断原生 Termux 可直接使用。[安装文档](https://hindsight.vectorize.io/developer/installation)

本项目取舍：借鉴分工和证据返回；整套框架首先在电脑上做对照。若采用，仍需适配 owner/group/private 的可见性与忘记传播，不能把 bank_id 或标签当成现有授权模型的自动替代。

### Graphiti / Zep：事实变化与历史追踪

官方实现强调事实的有效时间窗口、由 episode 追踪来源，以及语义、关键词、图关系组合检索。依赖包括图数据库后端；当前也列有嵌入式 FalkorDBLite 路径，Kuzu 被标为 deprecated。因此不能简单归类为“只能远程”，但同样没有据此证明原生 Termux 适配。[Graphiti 作者仓库](https://github.com/getzep/graphiti)

时态图的研究出发点是持续会话中不断变化的信息，而非静态文档检索。[Zep 论文](https://arxiv.org/abs/2501.13956)

本项目取舍：先用 SQLite 关联表保存人物—断言—来源—有效时间。只有当多人物、多跳关系查询成为实测瓶颈时，再考虑引入图数据库。简单个人偏好问题不应为了“知识图谱”多运行一个服务。

### Mem0：适合做轻量接入对照，但不能凭品牌认定已解决来源

论文研究从会话提炼、整合、检索记忆，并在 LoCoMo 上评价普通版和图版；其报告结果来自作者的模型与实验设置，不是本项目成绩。[Mem0 论文](https://arxiv.org/abs/2504.19413)

当前作者仓库明确区分库、自托管服务器和云服务，并有 LLM、embedding 配置。[Mem0 仓库](https://github.com/mem0ai/mem0)

代码核对发现：当前主链路会取最近会话与既有记忆，进行结构化提炼；LLM 调用异常会与“未提炼出内容”区分。不能照搬旧文章，把当前实现一概描述成旧版 ADD/UPDATE/DELETE 流程。[提炼实现](https://raw.githubusercontent.com/mem0ai/mem0/main/mem0/memory/main.py)

默认向量后端是 Qdrant，其适配器支持本地 path；因此“Mem0 必须运行远程 Qdrant 服务”不成立。[配置](https://raw.githubusercontent.com/mem0ai/mem0/main/mem0/vector_stores/configs.py)、[Qdrant 适配器](https://raw.githubusercontent.com/mem0ai/mem0/main/mem0/vector_stores/qdrant.py)

本项目取舍：可以作为同数据对照，尤其测接入成本与召回；它的 user_id、metadata、消息历史与我们的原始消息来源链不是同一个契约。接入时必须证明能回答“谁在什么时候说的”，以及删除、取消、旧助手错误不会再次污染事实。暂不能宣称原生 Termux 可直接安装成功。

### MemGPT / Letta：解决“重要信息每轮可见”，但现行产品已变

MemGPT 的核心是分层管理有限上下文与外部记忆。[MemGPT 论文](https://arxiv.org/abs/2310.08560)

核对时 Letta 主仓库已说明现行代码迁往 letta-code，旧 V1 API server 保留在 archive 分支。因此此前设计中的 v1-sdk 页面只能作为概念/旧接口参考，不能作为新部署教程。[Letta 主仓库](https://github.com/letta-ai/letta)

现行 letta-code 提供本地/云运行方式、消息搜索及可持续记忆上下文，是更完整的智能体运行时；其二进制发行支持列表不能直接作为 Termux 兼容保证。[当前代码与运行说明](https://github.com/letta-ai/letta-code)

本项目取舍：借鉴核心记忆块，给当前人物与目标范围编译一小份可撤销的稳定资料，不接管鱼脑的 QQ 生命周期、审批、发送确认和人格控制。用整个运行时替换现有系统，会把本次重构范围扩大太多。

## 2. 可落地的四种路线

下表是工程判断，前提仍是目前主要运行在手机上。

| 路线 | 适用情形 | 好处 | 代价与未验证项 | 当前建议 |
|---|---|---|---|---|
| A：SQLite 内重构 MemoryService | 保持现有手机架构 | 旧数据、权限、发送账本可保留；进程少 | 需要自行完成检索与来源契约，并跑质量评估 | 主线 |
| B：接入 Mem0 库 | 想尽快对照现成实现 | 可以替换/比较记忆后端，库模式不等于上云 | 原生依赖、角色来源、历史时态、删除传播需适配 | 隔离对照 |
| C：电脑/服务器 Hindsight | 有稳定外部运行环境 | 现成多路检索与来源返回，便于评估复杂查询 | 新常驻服务、同步、网络故障及远程数据边界 | 有外部机器时的备选 |
| D：Graphiti 或整套 Letta | 关系查询成为重点，或主动决定更换运行时 | 更完整的时态图或智能体上下文机制 | 接入面大；不能据宣传替代本项目验收 | 当前阶段不优先 |

不以 stars、作者各自 benchmark 的最高分进行排名；能安装也不等于适合手机长期运行。之前已发现的系统强停问题与记忆正确性要分开验证，增加框架本身不会修复手机后台回收。

## 3. 对原 v3 方案的具体收敛

### 3.1 小份核心资料 + 可搜索档案 + 原始证据

每次回复为当前说话人、当前隐私范围编译一小份稳定资料：用户固定的信息、经证据支持的高频事实、有效互动偏好。资料带来源 ID 与版本；按规则和明确预算选择，避免另造一个无限增长的人物摘要。

这能降低简单问题每次从零检索的失败率。核心资料也必须随更新和遗忘失效；它是资料数据，不是更高优先级系统指令。私人核心资料不能因为发言者是主人就进入群聊。

完整原始消息和语义事实继续可检索；提炼错误时允许回到原话，不能让丢掉细节的摘要成为唯一记忆。核心资料命中不代表历史来源已完整，要能按需展开。

### 3.2 语义检索成为完整验收的必要组成

分离查询、词法改进只是第一阶段。要宣称解决换问法，至少要有一个经过测试的语义通道。

推荐的正常路径是：本地索引 + 已配置的 embedding 服务；数据仍保存在手机，外部服务仅用于计算已允许范围的脱敏文本向量。是否使用外部 embedding 是配置选择，本轮没有配置或调用任何新服务。不能假定当前聊天地址支持 embeddings。

没有 embedding 配置时，以现有 LLM 分批筛选有效事实目录作为过渡模式，明确额外调用成本和扫描覆盖；不把它当作长期无限扩展方案。资料数量增长后，应以手机实测决定启用独立索引引擎或外部记忆后端。

完全本地 embedding 可以另做实验：

| 作者模型 | 已核实信息 | 在本项目的定位 |
|---|---|---|
| multilingual-e5-small | 384 维；查询和文档需要使用其训练要求的不同前缀 | 本地轻量候选，须实测中文口语、内存及运行时 |
| Qwen3-Embedding-0.6B | 0.6B 参数；支持多语言及可变输出维度 | 更大候选，先在电脑比较效果，再决定设备端价值 |

模型参数来自 [E5 作者模型卡](https://huggingface.co/intfloat/multilingual-e5-small)、[Qwen 作者模型卡](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)。模型卡没有提供本手机 Termux 的测试成绩，不能推断运行速度或安装可行性。也不要同时在手机常驻 embedding 模型和重排模型后再声称“轻量”。

### 3.3 检索、事实有效性、可信度分别处理

先限制 scope、人物与记录状态。分别检索用户断言、原始用户话语、需要时才使用的助手经历，防止助手经验淹没事实。至少保留两个不同粒度的检索对象：简短断言便于找答案，原始对话便于补足语境。

每路初期可取 20 条、合并后上限 80 条，作为调参起点而非正确性定理。来源重复只打包一次；时间和人物过滤不计作“相似度小幅加分”。排名融合后重排，再构建有限证据包。没有证据充分性判断时，不拿 RRF 分数或余弦值直接充当“我确定”的概率。

查询追问来源时优先 previous_readset；用户改问或出现新事实时再补查。前次 readset 的证据必须重新验证，不可把它当永远有效的缓存。

### 3.4 对“未知”建立可靠的程序状态

检索结果除了证据，还需区分 not_found、incomplete、unavailable、conflicting。网络失败、索引回填没完成、扫描预算用尽不能全部变成空列表。

回答涉及的来源 ID 必须真实存在、可见且有效；涉及原话和时间时可程序渲染。模型对语义支持关系仍可能误判，重要事实和冲突场景增加受限复核。不能因 JSON 字段合法就把整个自然语言回答判为真实。

## 4. 具体实现方案

```text
写入：原始事件 → 候选事实/互动偏好/真正约定 → 来源片段校验
                              → SQLite 事务 → 核心资料/关键词/语义索引

读取：当前用户问题 + 用户话题 + 上轮已用证据
          → 范围/人物/时间约束 → 多路召回 → 合并/重排
          → 原话展开/冲突处理 → 回答草稿 → 引用/版本校验 → 发送
```

保留现有 Store 事务，增加三个职责清楚的模块：MemoryService 编排，retrieval 提供可替换检索后端，evidence 提供原始来源及版本核对。聊天、心跳、行动共用它，平台模块继续负责收发。

新表以增量方式保存断言元信息、来源片段、检索版本与会话读集；不先推翻主表和旧 ID。embedding 缓存保存 model_id、dimension、content_hash、record_revision；失效记录可以先禁止检索，再异步回收向量，避免后台删除延迟导致复活。

新旧读链路先影子对照。若经过匿名评估发现现成库明显更好，可以通过同一 MemoryService 后端契约切换；上层事实有效性、隐私、发送校验不绑定某个框架。

## 5. 如何证明改进

LongMemEval 提供长期对话记忆评估；作者仓库还标记了 2025 年的数据清理和 2026 年的 V2。比较时必须注明具体版本，不能混用不同题库的百分比。[LongMemEval 官方仓库](https://github.com/xiaowu0162/LongMemEval)、[V2 仓库](https://github.com/xiaowu0162/LongMemEval-V2)

LoCoMo 官方公开集包含长会话及问答/事件标注，现行公开子集不是最早版本的全部 50 段会话。不同论文的数据选择、模型、评审方式和 token 预算可能不同，不做直接横向分数排序。[LoCoMo 官方仓库](https://github.com/snap-research/locomo)

对鱼脑具体实施四组对照：

| 组 | 配置 | 要回答的问题 |
|---|---|---|
| G0 | 现有实现 | 当前失败基线是什么 |
| G1 | 拆查询 + 分来源 + 原话展开 | 确定性读链路调整能改善多少 |
| G2 | G1 + 核心资料 + 语义通道 + 时态处理 | 换问法、更新、来源追问能否稳定通过 |
| G3 | 同数据的 Mem0/Hindsight 后端 | 自建是否值得，现成框架是否明显更优 |

每组使用同一模型、相同原始事件、隐私规则、检索预算和回答预算。语义 backends 不同的费用和耗时单列，额外抽取调用也计入。不能让某组偷偷获得所有历史或更多输出 token。

现有 24 个匿名案例先做核心回归，再扩成至少 100 个问题，划出不参与调参的测试集。严格区分：写入是否保存答案、召回是否带来正确原话、回答是否正确使用原话、引用是否真正支持结论。答对但引用错误不能算完全通过。

设备性能另外测：每轮调用数和 token、P50/P95、鱼脑 RSS、长时间锁屏后状态、断网降级、索引回填对 QQ 收包的影响。没有真机测量前，不承诺毫秒延迟、低内存或手机长期稳定性。

## 6. 开始实施时的顺序

1. 固定 G0 输出及来源 trace，补齐此前失败类型的匿名标注。
2. 实现统一读接口，优先处理当前问题稀释、来源混用、原始证据展开、时间和上一轮证据继承。
3. 接入可配置语义检索，制作核心资料投影，跑 G1/G2 对照；无语义的版本只能称第一阶段修复。
4. 重构写入分类、事实时态、事项状态机和互动偏好；迁移只重建有合法原始来源的投影。
5. 电脑上跑现成框架对照，按质量/费用/稳定性决定后端，随后统一心跳与行动链路。
6. 影子切换、备份与兼容回滚验证，再配套更新 APK 资源和手机运行模块。

本轮交付为资料与方案，以上工作未执行。既有 24 个用例也仍是验收规范，不能写成已通过的质量成绩。
