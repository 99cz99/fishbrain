# 记忆 v3 重构方案

状态：设计建议，未实现、未部署。2026-10-31。

后续资料核对与选型收敛见 [记忆系统资料与方案](memory-research-and-options-2026-10-31.md)。补充确认了 Hindsight 的来源展开能力、Graphiti 的嵌入式后端选项、Mem0 的本地库模式，以及 Letta 现行代码与旧 V1 接口的区别；不要将本文旧接口参考当作部署说明。完整语义能力仍须作为独立验收项，只有查询拼接调整不能称重构完成。

## 决策

建议对读写链路做一次有边界的重构，保留 SQLite、原始事件、来源追踪、删除墓碑、隐私范围、发送账本和现有 App 的管理入口。把聊天、心跳、行动共用的记忆入口统一到 MemoryService，逐步替换当前“混合文本相似度前八条”的用法。

核心目标是：先找证据，判断证据支持什么，再以自然语气回答。生成模型负责表达，数据库及证据校验负责身份、有效性、权限、版本和可追溯性。语义理解仍可能出错，不能把结构化输出包装成正确性保证。

本方案基于设备只读诊断、源码核对和匿名实验。没有改写用户现有记忆，没有进行真实模型评测。具体诊断见 memory-recall-diagnosis-2026-10-31.md。

## 为什么需要重构

目前数据库已经保存了不少必要信息，但读取接口把不同性质的数据放在一个池里竞争：用户事实、未完成问题、助手的自述和自身经历。一个统一的相似度阈值同时承担了找话题、找答案、判断可信度三个职责，它做不到。

本地匿名实验 `python tools/probe_memory_query_design.py` 的结果：

| 实验 | 当前拼接查询 | 只检索当前问题 | 启示 |
|---|---|---|---|
| 长背景稀释简短偏好 | 正确事实未进入上下文，相似度 0.0201 | 进入上下文，0.1691 | 必须拆开当前问题和背景 |
| 问“演奏哪种乐器”，记录只写具体乐器名 | 未召回 | 仍未召回，字符重叠为 0 | 去掉背景不能替代语义检索 |

这只是两个受控检索实验，没有调用 LLM，也不代表端到端回答准确率。

## 用户应看到的变化

- 已经说过的稳定事实，可以换个问法再问；回答优先使用原始用户证据。
- 追问“你从哪知道的”，能接着上一轮已用证据，取出时间和原话，不重新随机搜索一遍。
- 只查到较弱旧记录时，清楚表达证据强度；没找到时说“这次没有查到”，不断言“你从没说过”。
- 用户纠正事实后，之后回答使用新版本；问历史时仍能解释变化，除非用户选择忘记。
- 用户明确要求的互动方式有独立持久入口，不依赖“碰巧召回一条偏好”，也不变成智能体自己的性格。
- 闲聊自然，不向用户展示打分、内部 ID 或每轮证据列表；只有追问来源、发生冲突或需要澄清时解释依据。

## 一、存储分工与证据规则

### 1. 原始事件是依据，事实是可重建的理解

原始事件包含 event_id、平台消息 ID、说话人稳定 ID、会话、隐私范围、发生时间、记录时间、文本和修订版本。助手回复和工具结果也保留，但必须有不同的角色/来源类型。

原始事件保留已脱敏的用户话语；未经用户授权的内容不能因此获得更高指令权限。“不改写原始事件”不妨碍用户删除：忘记操作清理内容并留下去重墓碑，后续索引不能把它恢复。

语义事实是一个有来源的断言，而不是系统认定的客观真理。例如“某人说自己会游泳”属于 user_assertion。需要区分用户亲口陈述、工具观察、助手行动结果和推断。模型说“我记下了”既不能证明用户说过，也不能证明数据库成功提交。

每条断言至少保存：人物、话题、关系、值、肯定/否定/不确定、有效时间、来源 ID 与原话片段、生成模型/版本、处理状态。关系可以扩展，不靠一张写死的爱好关键词表。类型和 JSON 格式的验证不能替代语义核对。

### 2. 按“要回答的问题”选择来源

| 要回答的内容 | 合格的主要依据 | 不足以单独证明的内容 |
|---|---|---|
| 用户事实/偏好 | 同一人物的明确原话、用户手工纠正 | 助手对该用户的猜测、助手自己的道歉 |
| 当时双方说了什么 | 双方对应角色的原始消息、发送状态 | 把双方文字合成后无法区分说话人的摘要 |
| 智能体实际执行了什么 | 发送账本、执行结果、平台确认 | “我刚做完了”这类生成台词 |
| 智能体的行为特点 | 多次独立行为和外部反馈 | 同一人设驱动的重复自述 |
| 未完约定 | 明确承诺、请求或待反馈事项及其后续状态 | 普通即时问句、一次叹气、不完整输入 |

现有 experience 不删除，但从“用户事实”的默认候选通道移出；查询“你上次说什么”时仍可使用。先通过来源规则过滤，再排序，不能仅给 experience 减一个小分。

### 3. 补足对话语境，限制推断

整理记忆时读取事件所属会话的一小段相邻原始对话。每个参与者、每句话都有单独 ID、时间和角色，不能把助手提供的信息伪装成用户说过的事实。

例如相邻两句“我在练乐器”“古典吉他”，可以提议合成一条断言，但需要同时引用两句用户消息；若中间已经换话题或存在多个可能指代，保存原话并标为待澄清。背景只能帮助消解指代，不能替原话添加未被陈述的偏好、确定日期或身份。

提炼输出包括 assertion、question、acknowledgement、fragment、transient_state、commitment 等事件性质；question 等仍可检索原话，默认不升级为长期事实。分类器误判属于必须评测的风险。

### 4. 互动偏好和执行权限独立

明确的“以后跟我说话温柔一点”进入 interaction_preferences，绑定发言人、适用关系和范围、来源及修订版本。只有有权限的人可以改变相关控制；引用别人说的话不能成为新指令。

互动偏好与自动人格区分开，也不能越权覆盖既有审批、隐私、启用平台和静默设置。删除其依据时撤销派生条目，用户手工保留的控制按其独立来源处理。

## 二、更新与遗忘

事实变化需要区分两种时间：事情何时成立，以及系统何时得知。简单“新记录覆盖旧记录”会把晚到的旧消息误当最新事实。

- 一个属性可有多个值；“也喜欢另一种饮料”是补充，不是撤销之前的偏好。关系的单值/多值性质不明确时不自动互斥。
- 明确纠正关闭被纠正断言的当前有效性，保留变更链；历史查询可以按时间访问。
- 两条证据冲突但没有明确纠正关系时，返回 conflict，并询问或带时间说明；不能由相似度高低偷偷选一个真值。
- 区分存储冷热与事实有效性。因容量被 archived 的有效事实仍可从冷记录检索；superseded、deleted、quarantined 不得作为当前事实使用。
- 忘记必须覆盖事实、摘要、别名、搜索键、向量、证据片段、会话已读证据、画像、缓存和诊断中可能包含的正文。保留无正文的版本/去重标识。
- 普通新消息不应取消所有正在生成的回答；发送前核对本次实际使用的证据版本、删除 epoch、会话版本和控制版本。相关来源被删改时作废旧结果，不能只在检索时检查一次。

## 三、读链路

```text
当前消息 + 带时间/身份的近期用户话题 + 上轮使用的证据 ID
                       |
                 识别查询意图
       人物事实 / 对话回顾 / 来源追问 / 历史 / 闲聊
                       |
             先限制身份、范围和有效性
                       |
       当前问题索引 / 话题关系 / 语义 / 冷记录
                       |
            合并候选、去重、检查冲突
                       |
           展开原话和时间，构造证据包
                       |
       生成带支持来源的回答草稿 + 程序校验
                       |
             自然表达 + 发送前版本复查
```

### 1. 查询不再拼成一大段

分别保留 current_query、user_topic_context、requested_time 和 previous_readset。助手历史只能用于理解“你刚才为什么那么说”这类对话对象，不能作为用户事实的检索扩词来源。

允许一个小型、结构化查询计划：目标人物、意图、关系/话题、时间、原问题及最多两个语义改写。模型不能扩大程序给定的隐私范围，不能生成任意 SQL，不能把一个候选答案写进查询当已知事实。猜测扩词只能做搜索键，不能成为证据。

查询计划也会漏判，因此先运行低成本本地候选检索；记忆类问题、追问来源或出现证据冲突时进入较完整的读证据路径。路由漏判需要独立测量，不能只评估成功进入检索的请求。

### 2. 多路检索，至少有一种真正的语义通道

保留现有无可选 SQLite 扩展的字符索引作为第一路，改用独立查询和词频区分度评分；BM25 可改善排序，但不解决完全不同的表达。

第二路为事实的话题、关系、经依据核对的别名及可回答问题索引。这些结构在后台提炼时产生，可以连接简称和正式名称。模型生成的问题或标签只用于找到事实，不能反过来证明事实。

第三路为语义检索。推荐提供可替换 backend：

- 已配置并验证可用的 embedding：用脱敏后的原始片段/断言生成索引，向量保存在同一 SQLite 中。预先按权限过滤，不能先跨范围召回再让模型删私事。索引含模型、维度、内容哈希和版本，模型变更后重建而不混算。
- 默认没有 embedding 能力时：使用现有聊天模型，对同人物、同范围的简短事实目录分批选择候选，再读原始证据。目录是从有效断言实时投影的短条目，不是无来源摘要。不能默认全库一次塞入 prompt，也不能只看词法前 256 条后就声称“语义搜索”。

分批检索受总耗时和 token 预算约束，返回扫描覆盖信息。预算耗尽时只能说“本次检索不完整”，不能断言不存在。少量主题目录可帮助路由，但若主题选择不可靠，要允许补查。长期大量数据下，稳定的 embedding backend 可能成为性能需要，应由实测决定。

当前的模型供应商配置不能证明支持 embedding；方案不能要求用户在升级后突然另买服务。也不建议在 Termux 同时跑重型本地语言模型。

多路结果采用排名融合和去重，最终按问题所需证据重排；存储重要性与新近性只作为次要因素。不能因为新近错误回复频繁出现，就压过直接用户陈述。候选数、事实数和证据长度分别限额，预算以实际模型 token 或明确标注的保守估算管理。

### 3. 每轮证据包，而不是八条混合记忆

MemoryEvidenceBundle 至少包括：

```text
status: supported | conflicting | not_found | incomplete | unavailable
subject, scope, requested_time, knowledge_revision
claims: [{claim_id, statement, source_type, valid_time, evidence_ids}]
evidence: [{event_id, revision, actor, role, occurred_at, quoted_span}]
conflicts, search_coverage, previous_readset_id
```

这是设计字段，不是现有 API。supported 也不是“客观真实”，而是给定来源支持该断言。

检索结果必须展开有效原始来源。来源链做循环检测、深度和长度上限；每个节点重新校验范围、人物及版本。来源失效时不能只留下旧事实正文。对 source_ids 为空的旧记忆标注 legacy_unverified，不能临时编造出处或凭昵称绑定身份。

同一事件的事实与 episode 去重打包，避免占两个名额；多个独立来源在需要证明重复/变化时保留。按事实问题默认不注入无关人格 belief 和助手经验。

### 4. 连续追问继承“读过什么”

每轮按会话、人物和范围保存实际使用的 claim/evidence ID 及版本，不保存可复活已忘内容的独立正文缓存。下一轮问来源或原因时优先展开上轮使用的记录，必要时再补查。

继承不代表冻结事实：每轮检查原记录是否被纠正、删除或失效。话题改变、越过时效或进入另一隐私范围后，不复用旧读集；未确认发送的草稿不能当作用户已经看到的对话。

## 四、回答与核对

记忆类回答先生成结构化草稿：回答涉及的断言、各自依据以及自然语言 draft。程序核对所有引用确实来自本轮允许的证据包，时间/人物匹配、记录仍有效；需要明确出处时可以由程序直接渲染来源时间和原话。

语义上的“这句话是否真的由原话推出”仍可能被模型判断错。对于事实更新、冲突和重要来源追问，可以增加一次独立核对；普通检索不强制多加一轮。自评或同模型复核不是正确率保证，须测量它是否实际降低错误。

校验失败时最多进行一次受限修正；再失败就明确证据不足。不能无限重试，不把系统错误解释成用户没说过。输出应区分：

- not_found：本次没有查到足够依据；
- incomplete：检索预算耗尽或部分索引尚未就绪；
- unavailable：查询服务/模型暂不可用；
- conflicting：已有说法相互冲突，需时间限定或澄清。

减少“记忆不足就问用户”作为第一反应：先补查原话和已有读集，再请求用户重复。明确声称“已经记住”必须有提交成功结果；明确解释程序出错原因必须有运行诊断，不让聊天模型自行编造内部状态。

普通闲聊仍保留表达自由和情绪；事实可信度检查不应让每句话像数据库报告。误路由、漏标断言和表达时引入新事实都是剩余风险，必须端到端测试。

## 五、近期上下文、待办和人格

近期上下文改为带 id、时间、身份、渠道的结构，按完整对话轮和 token 预算选择。助手分三段发消息算同一回复轮，避免只取“最后两条”时两条全是助手台词。跨日/长间隔显式保留时间界线。原话只进入数据层，不提升为 system 指令。

动态话题摘要只作为检索导航，带来源 ID、版本和时效；不能单独支持事实，也不能替代原始记录。

待办改成明确状态机：open、resolved、cancelled、expired、needs_clarification。创建必须有明确未来动作、约定或待反馈对象；普通问句是当轮 conversation_question，不作为长期 intention。何时完成以相关事件或真实执行结果为依据，不能仅因“助手回答了点什么”就关闭。原有不确定发送结果仍禁止自动重发。

旧 intention 的清理先出审查清单，不批量无依据删除。未知日期可保留 due_at=0；“说了以后再聊”也不能自动安排闹钟。

自动人格继续独立处理，只接受具备相应行为来源的候选。仅引用了真实用户事件，不代表 experience 中助手对自己的描述就是真的。自述与行为之间需要明确关系，而不是“根节点非空就算有效”。

## 六、实现落点

| 模块 | 职责及改造 |
|---|---|
| memory.py / memory_system.py | 保留 Store 和事务；增加可追踪断言元信息、来源片段、有效性/冷热区分及版本查询 |
| 新 memory_service.py | 统一聊天/心跳/行动接口，编排写入、查询、证据读集和预算，定义类型契约 |
| 新 memory_retrieval.py | 独立查询、多路候选、排名融合、冷记录和语义 backend |
| 新 memory_evidence.py | 来源展开、冲突与时态处理、证据包及发送前校验 |
| autonomy.py | 后台提炼按对话原始证据生成候选，使用统一提交入口；普通问题不升级为待办 |
| qq_bot.py | 负责平台收发；不再内嵌查询拼接、记忆打包和事实裁决 |
| life.py | 通过同一 MemoryService 获取对应目标范围资料；保留第二阶段目标校验 |
| personality.py | 保留撤销和人工画像规则，补足来源角色与行为证明 |
| server.py / App | 管理来源、冲突、互动偏好、检索状态；兼容原记忆管理接口 |
| tools/sync_fish_assets.py / 向导资源 | 同步新增模块及清单，再打包验证；不能只替换手机单个模块 |

不引入独立图数据库或后台常驻向量服务。来源关系可以用 SQLite 关联表表达。向量和目录只是可丢弃重建的索引，SQLite 里的事件及有效断言仍是依据。

初步表设计采用增量：assertion_meta、evidence_links、memory_readsets、检索索引版本表。先保留 memories 主表及旧 ID，对旧接口做兼容投影；只有新模型验证稳定后才考虑拆分主表。不要一次替换所有存储格式与全部消费者。

## 七、迁移和发布

1. 冻结匿名评测和旧实现输出，记录有效证据命中、回答及来源，不边调参数边改验收题。
2. 增量建表、SQLite backup、迁移版本号和断点，旧库可重新打开且数据量/来源校验一致。备份留设备本地。
3. 先影子构建新索引，旧链路继续回答。影子结果不发送、不写人格、不创建待办。
4. 回填有明确事件来源的记录；旧 entity_id 为空或来源缺失的记录保留弱证据标记，不能按同名猜绑定。quarantined 和删除墓碑不重提炼。
5. 小批切换读链路，先验证 chat，再验证 heartbeat/action；所有消费者最终统一，避免只修 QQ 回复。
6. 后续切换写入、事项和偏好投影。新旧写入以同一事务及稳定事件 ID 去重，不双重调用模型。
7. 回滚使用读链路开关和兼容投影；运行期间已有新消息时，不能直接恢复旧备份丢掉新对话。失败的新投影可停用、保留来源后重建。

本轮不执行迁移或部署。

## 八、验收标准与测量

现有 unittest 验证程序约束仍应保留，但不足以证明真实语义效果。新增三层评估：

1. 确定性约束：身份、范围、删除、来源 ID、版本、时间过滤、发送状态和事务。必须全部通过。
2. 检索评估：正确证据是否进入候选、是否进入最终证据包，分离写入遗漏和读取遗漏；不以助手答对的偶然猜测算成功。
3. 真实模型端到端：固定模型/参数记录答案、出处、矛盾、拒答以及额外延迟和 token；模型升级后重跑。不能仅靠同一个生成模型自评。

人工标注的匿名用例见 `memory-v3-acceptance-cases.json`，为待执行的设计验收规范，不是已通过测试。覆盖：不同问法、无字面重叠、来源追问、旧错误污染、跨日、身份与隐私、更新、多值、歧义、遗忘、离线、迁移、上下文长期噪声。

建议首个发布门槛（目标，非现有成绩）：固定核心场景全部正确；扩展可答集有效证据命中率至少 95%；来源引用能对应原始记录的比例 100%；事实回答正确率至少 90%；无证据时不编造率至少 95%；已删除/越权记录进入 prompt 的次数为 0。对扩展集按类别报告样本数和置信区间，不用一个总分掩盖更新/拒答的失败。多次生成的随机波动也应报告。

来源“存在且有权限”可以程序保证；“语义足以支持回答”不能据 100% 引用有效率宣称已解决，须单独评审。

从两个匿名实验不能推导上述百分比，应扩充至少 100 个带干扰和变体的测试问题，并保留不参与调参的测试集。公开 LongMemEval 可补充测试，但不能用其成绩替代手机实际模型和聊天分布。

性能先测当前手机的 300 条事实、1 万事件及长期增长数据。普通闲聊优先维持原一次生成请求；复杂记忆路径初期允许多一次计划/读证据请求，生成和核对尽量合并，冲突复核按需执行。所有调用计入整轮预算、允许取消，后台索引低优先级，不占用 QQ 保活线程。给出每路耗时、额外模型调用数、token 和 P50/P95，再决定是否启用 embedding 或调整预算。没有手机实测前不承诺“无延迟”。

诊断默认只记录问题哈希、计划类别、候选/入选 ID 与版本、淘汰原因、覆盖、模型和时延。完整 prompt 回放应是用户可控、有保留期的本地功能，正文随忘记清除；清除后可能无法完整重放过去，这是隐私约束下的正常结果。公开报告只使用匿名合成场景。

## 九、实施顺序

- A：建立评测及只读检索 trace；拆开查询、区分来源、展开原话、保留时间/完整对话轮、继承上一轮证据。这一步解决可确认的读链路缺陷，不宣称已解决无字面重叠。
- B：增加有来源的语义断言、目录及语义 backend，验证候选覆盖；事实更新和冷热语义一并校验。这一步才覆盖换问法和跨会话知识。
- C：回答草稿的证据契约、冲突和失败状态，按需语义复核，统一 chat/heartbeat/action。
- D：收紧新写入，迁移旧低质量事项，补充互动偏好和人格行为依据；影子对照、设备验证后发布。

各阶段的硬边界是评测通过和可回滚，不按“增加了多少类/多少代码”判断完成。

## 参考与取舍

- [LongMemEval](https://arxiv.org/abs/2410.10813)：借鉴索引、检索、读取分段评测，以及时间和查询扩展。方案仍需在本项目测量。
- [Zep](https://arxiv.org/abs/2501.13956)：借鉴事实有效时间及来源关系的建模思想；不直接引入其服务或基础设施。
- [Letta memory blocks](https://docs.letta.com/v1-sdk/memory/memory-blocks)：借鉴少量常驻资料与外部可检索记忆的分工。这里的资料始终是受权限约束的数据，不成为更高优先级指令。
- [Lost in the Middle](https://arxiv.org/abs/2307.03172)：长上下文利用存在局限，因此“把全部聊天都塞进去”不作为架构保证。该论文不是当前配置模型的直接评测结果。
