排查时复测：历史图片的 `gchat.qpic.cn` URL 返回 HTTP 400；`get_image` 返回 `retcode=1200, message='file not found'`。复测发生在 QQ 后续重启之后，不能据此断言故障当刻的 `get_image` 也返回完全相同的结果。原程序吞掉了直接下载异常，且没有记录 `get_image` 的失败返回，历史日志无法恢复这部分细节。

历史 RawMessage 中的 `picElement.sourcePath` 对应文件目前确实存在于 Debian rootfs，直接在 Termux 中按该路径检查则不存在。`fish/qq_bot.py:_get_image_bytes` 只尝试 URL 和 `get_image` 的 `data.file`；既没有容器路径映射，也没有在图片 URL 再次失败后独立继续尝试文件。这使本地兜底不完整。Rkey 获取异常是故障时刻直接证据，本地路径问题是已验证的另一薄弱环节。

建议修复：优先恢复 NapCat 的 Rkey 获取；对可用的本地图片路径增加严格限定 rootfs 的读取兜底，并让网络、文件候选分别尝试。记录脱敏后的 HTTP 状态、API retcode、候选来源和错误类型，避免继续只给出笼统错误。

### 已复现的功能缺陷

`QQBot._on_message` 按空行拆回复，`_send_segments` 逐条调用 `send_msg`。第一条抛出 `SendUnconfirmedError` 时，异常直接跳出整个循环，剩余段落不会提交给 QQ。因此“不自动重发第一条”虽然正确，却同时中止了所有后续段落；上一阶段只说明发送确认迟到，未完整说明此影响。

此外，助手短期上下文和自身经历都在整轮发送成功后才写入。只收到第一段但确认超时的情况下，用户消息已入上下文，实际收到的第一段助手回复却没有入上下文。模型下次会看到“多个旧问题没有自己的回答”，存在重新回应旧话题的条件；尚未提交的段落也没有持久保存。

本机用模拟 NapCat 超时运行实际 `_on_message` 路径：模型返回 3 段，只调用发送 1 次；短期上下文仅有 `user`，没有 `assistant`；传输待确认表和事件队列均为 0。复现未发送真实消息。

当前代码没有保存并在重连后恢复“未发剩余段”的机制。它的 `_event_queue` 是接收到的事件队列，单工作线程处理，重连不清空；这在理论上允许积压旧事件继续处理，但扫描到的上述时段没有证明其为本次原因。QQ 内部也可能在接口超时后继续完成已提交的发送；因此不能仅凭内容像旧回复就判断是哪层补发。

目前最贴合已定位时间线的解释是：第一段超时造成后续内容中止，同时助手上下文漏写；后续新生成的回复重新回答旧问题。用户具体所指消息尚未逐句确认，因此这部分是有时间线支持的解释，不应写成所有重连后旧消息的统一定论。

修复应按段保存计划与状态，区分已确认、已提交但未知、尚未提交；在取得可靠确认后继续后续段，避免重复发送状态未知的段落。对上下文明确保留发送状态，不能把未确认内容直接当作已成功的行为经历。若调整等待时间，应同时处理 NapCat 先返回超时的问题，单纯延长鱼脑等待无效。
