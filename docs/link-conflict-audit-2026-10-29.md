## 范围与方法

- 后台事件提炼 → 情绪评估，与心跳心情写入的交互。
- 安装资源清单、暂存/切换/启动路径及 supervisor；未执行真实安装。

## 发现

### 1. P1：启用平台设置未约束实际工具与执行

位置：`fish/autonomy.py:176`（select_tools）、`:190`（_route）；`fish/server.py:1144`（_start_qq）、`:271`（_build_heybox）。

`enabled_platforms` 被展示给提示词和状态接口，但 select_tools 只按 drive、适配器是否存在以及成长开关筛选，没有按平台开关过滤。路由也不复查。QQ 启动依赖 ws_url，小黑盒接入依赖 token，二者都不依据 enabled_platforms。

复现：将 enabled_platforms 设为 `[]`，保留已构造的适配器，成长工具仍包含 `get_login_info`、`heybox_sign` 等。于是用户控制、模型看到的“暂无平台”和实际可执行能力相互矛盾。

建议：统一平台可用性判定，同时用于工具注册、执行前复查及入口接入；明确禁用是否也停止接收消息。不能仅依赖提示词表达平台禁用。

### 2. P2：静默时段限制只接到消息发送，没有覆盖戳主人

位置：`fish/autonomy.py:221`（_do_talk）、`:253`（_do_like）、`:265`（_do_poke）。

“半夜也能主动找我”关闭后，只有 _do_talk 在 00:00–08:00 返回；_do_poke 无相同判断，仍直接调用 QQ。点赞也不检查该限制。

复现：midnight_ok=false、模拟 02:00，_do_poke 仍调用一次 send_poke。戳一戳仍是主动联系，可能触发提醒。

建议：给主人发消息、戳一戳等联系动作共用静默门控，执行前统一检查；是否限制点赞另明确产品规则。

### 3. P2：界面允许选择 Claude/Gemini，但自主行动依赖的工具调用必定为空

位置：`app/lib/pages/settings.dart:796` 附近；`fish/brain.py:79`（chat_with_tools）、`fish/life.py:74`（heartbeat）。

非 openai provider 会退回普通 chat 并固定返回空 tool_calls。心跳只消费 update_mood、schedule_next_wake、set_drive 等工具结果，因此即使文字模型正常，drive 仍是 none；对话里的 publish 工具也不会执行。

复现：分别配置 anthropic 和 gemini，模拟文字调用成功，工具结果仍为空。该限制已在开发文档写明，但设置页以可选 provider 呈现，没有解释自主能力将失效。

建议：实现这些 provider 的工具协议，或在保存/展示时明确限制，并为心跳提供可校验的替代决策格式。

### 4. P2：浏览后的回喂继续使用只读工具，无法完成“看帖后评论”

位置：`fish/autonomy.py:22` 附近（DRIVE_TOOLS）、`:139`–`:157`（读结果回喂）；`fish/life.py:154`（decide_action）。

小黑盒 feeds/comments 仅在“好奇”工具集里；读结果回喂继续使用相同 drive 和 tools，该集合没有 heybox_comment 或 heybox_post。decide_action 又会丢弃不在工具白名单的返回，因此这一轮不能评论刚看到的帖子。

复现：模拟“好奇 → heybox_feeds”，第二次决策拿到与第一次完全相同的工具集合，没有评论或发帖工具。QQ 的 get_group_msg_history 等读结果也未进入现有回喂分支，读取结果在当前动作链中被丢弃。

建议：根据读结果生成下一步候选工具，允许经审批的评论动作，并将 QQ 读结果纳入受范围约束的结果回喂。

### 5. P2：审批与执行结果之间缺少可查询的完成状态

位置：`fish/server.py:218`（execute_approval）、`:258`（_execute_recorded_action）、`:1045` 附近（审批 HTTP 分支）；`app/lib/pages/approval.dart:40`。

HTTP 先把审批从 pending 改为 approved，再启动发布线程并返回成功。后台即使拿到 `ok=false` 或遇到异常，也只记录经历/部分日志，不更新可查询的执行状态；App 只查询 pending，请求已经从页面消失。适配器不可用时，部分发布分支同样没有向请求方返回执行失败。

approved 可以合理地表示“授权通过”，但目前没有独立的执行成功/失败/结果未知字段和查询路径，用户无法从审批流程判断动作是否完成。

复现：模拟 QQ 空间发布返回 `ok=false`，执行结束后审批仍只有 approved 状态，失败不会回到审批页面。不能据此自动重试，尤其发送结果未知时可能重复发布。

建议：保留授权状态，另建 execution_state/result，并提供历史查询和 UI 反馈；区分失败与未获确认。

### 6. P2：纠正待办内容会使其变成事实，跟进链路丢失

位置：`app/lib/pages/memory.dart:105`（_edit）；`fish/memory_system.py:449`–`:464`（update_memory）。

记忆页允许纠正待办文本，但后端对任何内容纠正都先忘记原记录，再以 kind=fact 新建，未保留 intention 类型、due_at、last_attempt 等状态。

复现：创建已到期、可被 due_intentions 找到的待办，纠正文字后新记录是 fact、due_at=0，待办列表及主动跟进均无法再选中它。UI 仍把该动作称为纠正记忆。

建议：按记录类型定义纠正规则。待办文字修订须保留类型和明确的调度状态；对 belief/experience 的人工纠正也应明确是否转换为人工事实。

### 7. P2：旧事件提炼把当前心情的时间戳回拨，导致重复衰减

位置：`fish/autonomy.py:340` 附近（process_memory_batch 调用 _nudge_mood）、`:360`–`:397`（_nudge_mood）。

事件提炼把 occurred_at 作为 mood_at 传入；_nudge_mood 却先读取“已衰减到现在”的心情，在此基础上叠加情绪，再把时间戳写成旧事件时间。下次读取又把整份当前心情从旧时间衰减一次。

复现：当前心情时间戳为 now，处理一天前的事件后，存储的 mood_at 回拨一天。积压、失败重试及旧 QQ 事件都可触发，不仅旧事件贡献受影响，原有当前心情也被额外衰减。

建议：按事件年龄衰减该次增量，再以当前时间写回；或严格按时间顺序重放，但不能混用当前状态和历史时间戳。

### 8. P2：心跳与后台情绪评估并发写同一状态，后写入会覆盖更新

位置：`fish/life.py:55`（_save）、`:74`–`:150`（heartbeat）；`fish/autonomy.py:65`（后台线程）、`:360`（_nudge_mood）。

心跳在调用模型前读取四维心情；只要模型返回 update_mood，就用该旧快照补齐未提供的维度并整体写回。模型等待期间，后台事件评估可以已经更新了同一份状态。_nudge_mood 自己持锁并不能防止心跳随后写入旧快照。

复现：在心跳等待模型时模拟后台增加 valence 和 dominance；模型仅更新 arousal，心跳结束后 valence、dominance 均回到旧值 0。即使模型只改一个维度，其余维度的新变化仍丢失。

建议：对 life_state 加版本校验，在提交时重读当前状态并按字段/增量合并；不要跨模型等待持有数据库锁。叫醒、重置人格与正在进行的心跳写入也应使用同一版本控制机制。

### 9. P1：人工纠正事实仍可被更早的积压事件覆盖

位置：`fish/memory_system.py:307`–`:310`（旧事件保护）、`:449`–`:464`（人工纠正）。

人工纠正会新建无 source_ids 的 fact，注释称其 authoritative。但旧事件保护仅在目标存在 source_ids 时比较 occurred_at，恰好绕过人工纠正记录。更早收到、稍后提炼的事件仍可通过 replaces 覆盖这条人工事实。

复现：先存一小时前的待处理事件，随后人工纠正事实，再提交旧事件提炼结果并引用人工事实作为 replaces。新结果成功写入，人工事实被标为 superseded。这确认了存储层缺乏优先级保护，不表示真实模型每次都会提出该替换。

建议：显式保存 origin=manual/model、有效时间和修订版本；至少拒绝人工纠正之前的旧事件覆盖人工结果。之后的新明确陈述能否取代人工纠正，需要定义规则，不能把“人工永远不可更新”当成默认修复。

### 10. P2：来源已删除或人格已重置，旧提炼结果仍能改写心情

位置：`fish/autonomy.py:335`–`:347`（提炼结果与 appraisal）；`fish/memory_system.py:272`–`:282`（来源复查）；`fish/server.py:754`（reset_persona）。

apply_episode_result 检测到来源已失效后返回 0，但 0 同时也表示“批次有效、没有生成事实”。调用方未区分这两个结果，继续应用旧 appraisal。人格重置清空心情后，在途模型结果可以再写入旧事件情绪。

复现：模型请求期间删除全部来源并清空 life_state，再返回带 appraisal 的结果。记忆未复活，但重置后的 dominance 和 valence 重新变为 0.4。

建议：返回明确的批次接受状态，并对整个结果（记忆、积分、心情）校验来源和重置代次；只修记忆插入或只加锁不够。

### 11. P2：自省日志将未应用的建议记录为已生效设置

位置：`fish/memory.py:391`（apply_evolved_settings）；`fish/autonomy.py:588`–`:591`（成功日志）。

存储层正确阻止锁定字段及审批、静默、平台字段的自动修改，但 evolve 无条件记录“新设定已生效”，下一行输出的还是模型建议，未重读实际值。

复现：人工将 chat_scope=clean、midnight_ok=false 锁定；模型建议 all/true。实际设置仍为 clean/false，日志却显示 all/true 已生效。这是审计语义错误，不是上述限制已被绕过。

建议：apply_evolved_settings 返回 applied/skipped/unchanged 及原因；日志与成长状态展示真实应用结果。界面应说明保存行为设置会锁定整组提交字段，即使某字段本次没有改变；目前没有解锁入口，不能把成长开关理解为重新放开这些字段。

### 12. P2：表情包标签移出 system 时，连同输出格式教学一起丢失

位置：`fish/qq_bot.py:111`–`:112`（语法教学）、`:1252`（聊天 prompt 调用）、`:1276`（资料块）。

本次提交把标签放入 available_stickers 数据块是正确的信任边界调整；但调用 build_system_prompt 时不再传 stickers，导致 `[表情包:描述]` 的格式教学也不再生成。后续解析器仍只识别该格式，模型只看到标签清单，不知道约定的调用语法。

复现：实际使用的无 stickers 参数构造路径缺少该教学；传入非空标签时旧教学才存在。该探针确认协议说明缺失，不证明真实模型必定不发任何表情包。

建议：固定的输出协议留在 system，动态标签列表留在资料块；新增真实聊天 prompt 构造测试，不能把不可信标签重新拼回 system 来修复。

### 13. P2：聊天尺度只注入被动 QQ 回复，主动消息不继承

位置：`fish/qq_bot.py:82`（build_system_prompt）；`fish/memory_policy.py:55`（render_identity）；`fish/life.py:172`（_action_prompt）；`fish/autonomy.py:221`（_do_talk）。

clean/moderate/all 在被动回复中转成语言约束，但主动消息使用 render_identity 和 _action_prompt，二者都没有渲染 chat_scope。_do_talk 直接发送生成文本。因此“用户锁定聊天尺度优先”在存储层成立，在主动输出提示中仍未接通。

复现：其他内容完全相同时，分别以 chat_scope=clean/all 构造主动陪伴 prompt，两份提示完全相同。该证据说明控制输入缺失，不证明模型一定输出违规用语。

建议：将共同输出规则放到共享渲染器，明确其与底层人设、人工画像、自动特质、临时心情的先后；被动聊天与主动发送都用它，避免各维护一份尺度说明。

## 改动正确性与联动清单

方向正确且有现有测试支持的部分：外部数据从 system 移出、统一人格渲染、原始来源保留与撤销、人工画像版本校验、后台提炼调度、全量 Python 安装资源同步。这些改动应保留，不能因为残留问题整体回退。

需要区分的语义：approved 是授权结果，confirmed 是平台确认，二者都不表示他人已读；没有新增特质不等于自省失败；模型提出设置不等于设置已应用；按字符匹配的检索不保证识别同义句。

## 其他边界

`server.command` 中一般文字指令目前只记录日志和 working 状态，restart 返回“待接入”；这属于源码明确标出的未完成入口，本次不计入以上 13 项。不能把“已记录指令”理解为已经执行任务。

此前报告里的 global/self 人格输入断点、无关记忆变更清空整份画像、画像陈旧覆盖和资源不同步，在当前源码已有相应修复；本次没有把旧报告直接当成现状。现有回归通过只能证明已覆盖案例，不代表以上跨模块链路正确。

本报告未验证手机正在运行的版本、平台真实协议兼容性、真实模型提炼质量或长期负载。修复应按前述依赖顺序推进，先保护控制和数据，再补齐能力及用户反馈。
