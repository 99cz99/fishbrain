# QQ 快捷登录与扫码恢复（2026-10-30）

> 审查更正：本文初查曾把 Login 目录账号命名空文件称作凭据。文件实际用途尚未证实，不能由 0 字节直接判定票据丢失或必须 chroot。以 [后续完整链路审查](qq-login-chain-audit-2026-10-30.md) 的证据分类为准。

## 检查结果

- 鱼脑 API 正常；故障时 QQ 标为运行，但账号和 OneBot 均不在线，8081 未监听。
- WebUI 6099 曾监听但鉴权请求超时，之后也曾关闭。此时快捷登录列表查询失败，不能将返回的空列表当成“确定没有缓存”。
- 手机 QQ Login 目录中两个以账号命名的文件均为 0 字节（角色未证实）；既有“保存了 QQ 号”不代表已经保存可跨进程恢复的凭据。
- 旧快捷登录回退重启反复记录 QQ 停止超时。当前停止命令按参数匹配 `qq --no-sandbox`，也会匹配携带同一启动字符串的 proot/bash 启动器，存在把启动器与被跟踪程序一起终止的风险。
- 单次重新出码请求自身会同步等待停止及额外 3 秒，调用方可先超时，不能因此再次盲目提交同一请求。
- 当前 proot 实际版本为 5.1.107.101；只读 true 命令在兼容和默认模式均约 0.42 秒完成。未据此修改 seccomp 参数，也不能据此证明 QQ 工作负载无容器兼容问题。

## 本轮恢复

使用专用恢复脚本先在手机本地备份数据库、Login 目录及可用设备注册记录。暂停鱼脑以避免自动恢复竞争；先对真实 QQ 主进程发送 TERM，保留退出窗口，再清理已核对 UID、会话组和 QQ 启动参数的残留专属进程组。最后只启动一次不带 -q 的扫码会话，并恢复鱼脑守护脚本。

新二维码正常生成后，用户完成扫码授权。最终只读验证：

- `/qq/status`：online=true、stale=false。
- NapCat WebUI：isLogin=true、isOffline=false、loginPhase=ready，鉴权请求约 0.03 秒完成。
- 6099、8081 均监听；OneBot 接收与消息处理线程存活。
- 快捷登录列表现含当前配置账号，但上述文件仍是 0 字节。

恢复没有删除或重置账号数据、修改设备标识、改变 proot 兼容参数或发送测试消息。运行源码与 APK 未因本轮诊断再次替换，版本仍为 1.0.45+59；仅新增诊断和受控恢复工具。

## 剩余问题

本次确认扫码会话已经恢复，未通过退出已登录 QQ 来验证跨重启免扫码；真实票据位置及跨重启持久化根因仍未查实。App 的快捷登录回退/停止流程、WebUI 查询失败与空缓存的区分，以及旧日志信号的优先级仍需独立修复，不能把本次恢复描述为这些代码问题已解决。
